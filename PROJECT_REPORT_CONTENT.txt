1. ABSTRACT

SafeHeader Audit is a lightweight Python-based website security configuration checker. It examines the initial HTTP response of a supplied website and records selected security headers, basic HTTPS URL usage, HTTP status, and visible CORS response-header configuration. The application generates HTML, JSON, and CSV reports to make the observations easy to review and preserve. The project is intended as an educational demonstration of HTTP communication, Python programming, basic web-security configuration, error handling, and report generation. It is not a full penetration-testing tool, and all findings require contextual validation.

2. INTRODUCTION

Web applications rely on HTTP response headers to communicate security-related browser policies. Examples include Content-Security-Policy, Strict-Transport-Security, X-Content-Type-Options, X-Frame-Options, Referrer-Policy, and Permissions-Policy. Cross-Origin Resource Sharing (CORS) response headers also influence whether browser-based code from another origin can read a response. SafeHeader Audit provides a small, repeatable way to inspect these values.

3. PROBLEM STATEMENT

Manual review of response headers can be inconsistent for beginners. A simple tool is useful for collecting a standard set of observations and presenting them in a consistent report. However, header presence alone cannot prove that a website is secure, and missing headers do not always imply a vulnerability.

4. OBJECTIVES

- Build a Python tool that requests a user-supplied website URL.
- Capture HTTP response status and selected response headers.
- Check HTTPS URL usage.
- Identify missing selected security headers for further review.
- Summarize visible CORS configuration.
- Export results to HTML, JSON, and CSV.
- Handle malformed URLs and common connection failures gracefully.
- Encourage authorized, ethical security testing.

5. SCOPE

The project checks the first HTTP response reached from the supplied URL. It does not crawl pages, test login flows, perform active exploitation, assess application logic, validate all TLS settings, or guarantee detection of vulnerabilities. It is suitable for a small educational demonstration and can be extended later.

8. SYSTEM DESIGN AND METHODOLOGY

Workflow:
User enters authorized URL
        ↓
Validate and normalize URL
        ↓
Send one HTTP GET request with timeout
        ↓
Capture status, final URL, and response headers
        ↓
Check HTTPS usage, selected security headers, and CORS headers
        ↓
Create findings and recommendations
        ↓
Export HTML, JSON, and CSV reports

9. IMPLEMENTATION

The application is implemented in app.py. The normalize_url function checks the input scheme and hostname. The fetch_response function sends a GET request and handles HTTP error responses as responses with useful status/header information. The audit function collects response data and creates findings. The reporting functions export the findings to HTML, JSON, and CSV. The application uses the Python standard library, so no third-party installation is required.

10. SECURITY CHECKS

- HTTPS URL usage: notes whether the supplied URL uses HTTPS. This is not a complete TLS assessment.
- Content-Security-Policy: checks whether the response includes a CSP header.
- Strict-Transport-Security: checks whether HSTS is present.
- X-Content-Type-Options: checks whether the header is present.
- X-Frame-Options: checks whether the header is present.
- Referrer-Policy: checks whether the header is present.
- Permissions-Policy: checks whether the header is present.
- CORS: records Access-Control-Allow-Origin and Access-Control-Allow-Credentials and flags combinations that warrant review.

Severity labels are guidance for prioritizing review, not proof that a vulnerability can be exploited.

14. LIMITATIONS

- Only the initial response is checked.
- No site crawling or authenticated scanning.
- No active exploitation or intrusive testing.
